## Finding 1: Preparation identity collapses before the promised local exact match
- Severity: High
- Location: Phase 2, Requirements (lines 44-51), Architecture And Data Flow (lines 68-73), Implementation Steps 2-4
- Flaw: The plan makes `preparation` an explicit identity input, then sends a normalized lookup name through the existing exact `food_reference` key without defining how preparation survives normalization. The repository's declared normalization source of truth removes `raw`, `cooked`, `boiled`, `fried`, `grilled`, and `baked`, while the table permits only one row per normalized key. With the no-migration boundary, the local store cannot distinguish the preparation variants the plan says it will evaluate.
- Failure scenario: `100 g raw potato` and `100 g boiled potato` both normalize to `potato`; the first verified local row wins and suppresses FatSecret lookup, so the resolver returns preparation-incompatible macros while reporting a confident local reference.
- Evidence: `src/domain/services/meal_suggestion/ingredient_name_normalizer.py:1-6` declares the normalizer the single source of truth; `src/domain/services/meal_suggestion/ingredient_name_normalizer.py:10-16` lists preparation tokens as removable qualifiers; `src/domain/services/meal_suggestion/ingredient_name_normalizer.py:43-62` removes them; `src/infra/database/models/food_reference_model.py:30-32` makes `name_normalized` unique.
- Suggested fix: Define a preparation-aware lookup contract before implementation: which preparations may use the preparation-agnostic local row, which must bypass it for a prepared FatSecret query, and how conflicts fail closed. Add paired raw/boiled/fried cases that prove a local hit cannot erase preparation semantics without adding a DB/mobile/RAG scope expansion.

## Finding 2: The proposed macro validator contradicts the repository's existing trusted-reference contract
- Severity: High
- Location: Phase 2, Requirements (lines 52-54), Implementation Step 3
- Flaw: The plan invents `protein+carbs+fat <= 105g`, `fiber <= carbs`, and `sugar <= carbs` as hard validity rules. The existing reference publication contract uses a 110 g total-macro tolerance and deliberately accepts verified records where fiber or sugar exceed carbs. The plan provides no source or calibration corpus that justifies reversing those established semantics.
- Failure scenario: A verified, rounded provider/reference record accepted by catalog publication is rejected by parse-text. The same `food_reference` row therefore resolves in one backend feature but produces AI fallback or 422 in another, making source authority endpoint-dependent.
- Evidence: `src/domain/services/meal_recommendation/ingredient_quantity_conversion_service.py:154-192` checks completeness/non-negativity and uses a 110 g macro-mass ceiling without component-versus-carbohydrate rejection; `tests/unit/domain/services/meal_recommendation/test_ingredient_quantity_conversion_service.py:211-221` locks acceptance when fiber/sugar exceed carbs.
- Suggested fix: Reuse the existing 110 g trusted-reference invariant and its component semantics, or document new empirical evidence and an explicit compatibility decision. The Phase 3 corpus must measure false rejection of currently verified rows before any stricter constant becomes a gate.

## Finding 3: The staged FatSecret detail contract does not contain the fields the plan expects to validate
- Severity: High
- Location: Phase 1, Requirements (lines 44-46); Phase 2, Requirements (lines 52-58); Phase 3, Requirements (lines 38-48)
- Flaw: The plan never defines whether fiber and sugar are required, optional-zero, or unavailable for a FatSecret detail. The live adapter maps `calories_100g`, protein, carbs, fat, serving description, and units only. Therefore “incomplete structured macros,” fiber/sugar inequalities, backend calorie derivation, and provider-energy tolerance cannot all have deterministic semantics from the actual mapped response.
- Failure scenario: If fiber/sugar are required, every current FatSecret detail is rejected as incomplete. If they silently default to zero, a high-fiber food is accepted as FatSecret but backend calories are derived with fiber zero, overstating energy and making the provider-energy comparison self-inconsistent.
- Evidence: `src/infra/adapters/fat_secret_service.py:345-366` is the complete structured detail mapping and omits `fiber_100g`/`sugar_100g`; `src/domain/model/nutrition/macros.py:19-30` shows fiber changes canonical calorie derivation; `tests/unit/infra/adapters/test_fat_secret_service.py:207-236` only proves the current P/C/F detail shape.
- Suggested fix: Add an explicit FatSecret mapped-detail schema to the plan, name required versus optional fields, and state how missing fiber affects acceptance and the energy check. Base fixtures on the adapter's mapped shape, not an assumed vendor payload, and require adapter-contract cases for absent, null, and non-numeric nutrients.

## Finding 4: Reference fiber and sugar cannot reach the public response or its calorie calculation
- Severity: Critical
- Location: Phase 2, Requirements (lines 52-56), Related Code Files (lines 80-95), Success Criteria (lines 148-154)
- Flaw: `NutritionResolver` carries fiber/sugar in `Macros`, but the app DTO used by parse-text has no fiber/sugar fields. The API mapper conditionally reads `item.fiber`; when absent it derives calories with fiber zero, and the public Pydantic DTO defaults both fiber and sugar to zero. The plan does not list `src/app/schemas/meal_schemas.py` for modification, so “structured reference owns macros” is impossible across the actual API boundary.
- Failure scenario: A 100 g reference with 20 g carbs and 10 g fiber is resolved correctly internally, then flattened to P/C/F. The route calculates 80 carbohydrate kcal instead of the canonical 60 and returns `fiber: 0`, while `data_source` still claims the structured reference.
- Evidence: `src/domain/services/nutrition_resolver.py:55-67` scales fiber and sugar into `Macros`; `src/app/schemas/meal_schemas.py:10-22` drops them from `ParsedFoodItemDto`; `src/api/routes/v1/meals_route_helpers.py:23-39` substitutes zero fiber when absent; `src/api/schemas/response/meal_responses.py:46-65` exposes fiber/sugar publicly with zero defaults.
- Suggested fix: Add the internal DTO and mapper path to Phase 2 scope while preserving the existing public field names. Require route-level fixtures proving reference fiber/sugar survive both authenticated and guest mappings and that route calories use the same resolved fiber.

## Finding 5: “Truthful” local source mapping silently widens a public enum-like contract
- Severity: High
- Location: Phase 2, Requirements (lines 47-49), Implementation Step 6, Success Criteria (lines 153-154)
- Flaw: The plan says to expose an accepted local record's origin source “truthfully,” but `food_reference.source` is an unconstrained database string, while parse-text currently emits only `fatsecret` or `ai_estimate` and the public DTO documents `usda`, `fatsecret`, or `ai_estimate`. Passing through values such as `catalog_seed`, `commissioned`, or `verified_seed` is a backward-incompatible response semantic change despite an unchanged JSON shape.
- Failure scenario: A mobile/web consumer switches on the documented values and treats `catalog_seed` as unknown, losing source labeling or rejecting an otherwise valid parse-text response.
- Evidence: `src/infra/database/models/food_reference_model.py:53-55` stores an unconstrained source string; `src/domain/services/meal_recommendation/ingredient_quantity_conversion_service.py:38-46` proves additional live source values exist; `src/app/handlers/command_handlers/parse_meal_text_handler.py:254-266` and `src/app/handlers/command_handlers/parse_meal_text_handler.py:299-310` show current parse-text values; `src/api/schemas/response/meal_responses.py:58-60` documents the public values.
- Suggested fix: Specify an explicit internal-origin-to-public-`data_source` mapping limited to the existing public values, and test every approved local origin. Do not pass the database source string through the API without a separately approved public-contract change.

## Finding 6: Schema retry and semantic retry have no single call-budget contract
- Severity: High
- Location: Phase 1, Requirements (lines 41-46), Implementation Step 2; Phase 2, Requirements (lines 59-62), Implementation Step 8
- Flaw: Phase 1 promises exactly one schema-validation retry and zero extra AI retries on provider outage. Phase 2 separately adds one semantic retry whenever unresolved fallback is unsafe. The plan never states whether these share a two-call request budget, stack to three calls, or which retry wins after a malformed first response followed by an unresolved reference.
- Failure scenario: First AI output is schema-invalid, the schema retry succeeds, FatSecret then times out, and the estimate fails density checks. One implementation makes a third AI call and breaks the characterized call/latency contract; another raises 422 without the promised semantic retry.
- Evidence: `src/app/handlers/command_handlers/parse_meal_text_handler.py:39-40` fixes the current validation attempt count at two; `src/app/handlers/command_handlers/parse_meal_text_handler.py:143-186` owns the only current AI retry loop; `src/app/handlers/command_handlers/parse_meal_text_handler.py:263-310` performs provider fallback without another AI call.
- Suggested fix: Define one request-wide AI attempt state machine and total call ceiling, including malformed output, AI-provider outage, reference miss, reference timeout, and unsafe density. Phase 1 tests must assert the exact call count for each combined sequence, not isolated retry cases only.

## Finding 7: The timeout wording does not bound a 20-item request
- Severity: High
- Location: Phase 2, Requirements (lines 48-62), Implementation Steps 4-5, Risk Assessment (lines 162-163); Phase 3, Requirements (lines 49-50)
- Flaw: “One bounded timeout budget” is not defined as per item or per request, and the plan leaves the handler's item loop architecture intact. The current handler awaits lookups serially and the internal contract allows 20 items. A per-item search/detail timeout therefore multiplies into request-level latency; Phase 3 explicitly refuses a latency gate for the first release.
- Failure scenario: A valid 20-item parse hits slow FatSecret misses. Serial search/detail resolution consumes the timeout repeatedly, holding the authenticated request and the guest quota reservation for tens of seconds even though each individual lookup respects its timeout.
- Evidence: `src/domain/model/ai/nutrition_contracts.py:278-288` permits 20 text items; `src/app/handlers/command_handlers/parse_meal_text_handler.py:90-95` resolves them sequentially; `src/app/handlers/command_handlers/parse_meal_text_handler.py:268-271` applies the current timeout inside each item lookup.
- Suggested fix: State a request-wide external-resolution deadline, total provider-call cap, bounded concurrency policy, and deterministic partial-fallback ordering. Make the maximum-item slow-provider case a release gate; reporting p95 without a threshold does not bound production request time.

## Finding 8: The plan's “all callers” claim has no complete consumer inventory
- Severity: Medium
- Location: Phase 2, Implementation Step 7, Todo List line 143, Related Code Files (lines 80-93)
- Flaw: The plan says to update constructor assertions “for every caller” without naming or counting them, and it calls `NutritionResolver`/the staged provider “reused” without stating their actual current consumers. The complete live inventory is: seven direct `ParseMealTextHandler` constructions (one production, six unit); `MealTextNutritionResponse` has one runtime consumer plus its re-export/tests; `NutritionResolver` has zero production consumers and three unit constructions; staged FatSecret search/detail are consumed by `FoodReferenceValidationService` and internally by `FatSecretService.search_foods`, with the adapter delegator/tests as contract consumers; the public mapper is shared by two routes. This is a new production use of `NutritionResolver`, not a behavior-preserving reuse.
- Failure scenario: The constructor changes are made only in `event_bus.py` and singleton tests, leaving six direct handler tests/fakes stale; or shared staged-response semantics are changed for parse-text and silently alter image validation/search enrichment because their consumers were not included in the review matrix.
- Evidence: `src/api/dependencies/event_bus.py:505-513` is the sole production handler construction; `tests/unit/handlers/command_handlers/test_parse_meal_text_handler.py:84`, `:158`, `:198`, `:233`, `:257`, and `:306` are the six direct unit constructions; `src/domain/services/nutrition_resolver.py:33-68` has no production caller found and `tests/unit/domain/services/test_nutrition_resolver.py:17-70` contains all three current constructions; `src/app/services/food_reference_validation_service.py:74-84` consumes staged methods; `src/infra/adapters/fat_secret_service.py:189-228` consumes them through the enriched wrapper; `src/api/routes/v1/meals_manual_text.py:141-180` and `src/api/routes/v1/meals_manual_text.py:185-258` are the two public consumers of the shared mapper.
- Suggested fix: Add this counted inventory to Phase 2 and assign a compatibility assertion to each consumer group. Explicitly state that `NutritionResolver` gains its first production caller and that shared FatSecret method shapes cannot be changed for parse-text without re-verifying `FoodReferenceValidationService` and `search_foods()`.

## Finding 9: A handler-level harness cannot prove the advertised public response-contract gate
- Severity: High
- Location: Phase 3, Requirements (lines 41-48), Architecture And Data Flow (lines 53-62), Implementation Steps 2-8
- Flaw: The harness architecture invokes the handler, but the public response contract is assembled after the handler by route-specific code and a separate mapper. Therefore “response contract 100%” inside the proposed evaluator cannot observe public calories/fiber/sugar/defaults, authenticated exception mapping, or guest reservation release/completion behavior.
- Failure scenario: Offline and live harnesses pass on a correct `ParseMealTextResponseDto`, while the actual route drops fiber, derives different calories, or maps semantic exhaustion differently. The release gate reports 100% contract compatibility although neither HTTP path was exercised.
- Evidence: `src/app/handlers/command_handlers/parse_meal_text_handler.py:119-141` returns the app DTO; `src/api/routes/v1/meals_route_helpers.py:23-39` performs the public item mapping; `src/api/routes/v1/meals_manual_text.py:168-182` maps authenticated responses/errors; `src/api/routes/v1/meals_manual_text.py:240-258` has distinct guest quota/error and response behavior; `scripts/development/evaluate_meal_analyze_prompt_candidates.py:15` shows the referenced evaluator pattern imports a domain loop rather than an API route.
- Suggested fix: Split the gate claims: handler semantic metrics belong in the corpus evaluator; public compatibility must be proven by explicit authenticated and guest route tests using the shared mapper and controlled 422 path. Do not label handler-only live runs as API-contract proof.
