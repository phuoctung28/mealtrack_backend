## Overview

- **Priority:** P1 — critical recommendation business logic.
- **Status:** Completed.
- **Goal:** make current v1 behavior, persistence replay, HTTP shapes, and performance boundaries executable specifications before refactoring.
- **Scope:** tests and baseline evidence only; production behavior must not change.

## Key Insights

- V1 scores `0.82 * calorie_fit + 0.18 * raw_affinity` and ties by catalog meal ID.
- The optimizer ranks once per meal type, applies `20%`, then `30%`, then absolute-calorie fallback, and persists 9 winners plus 45 alternatives.
- Idempotent create returns the stored plan before reading catalog/history, so replay is already the boundary that protects old algorithm versions.
- API output intentionally differs by operation: compact create/read; one-slot detail for detail/swap/log.
- Existing local performance evidence is synthetic; do not claim staging latency from it.

## Requirements

### Functional

- Freeze v1 selections and six-decimal scores for cold, sparse, medium, and dense history profiles.
- Lock published/active, cuisine, meal-type, positive-calorie, uniqueness, tolerance, fallback, insufficiency, stable-tie, 9-slot, and 45-alternative behavior.
- Prove idempotent replay performs no catalog, history, or optimizer work and returns the persisted plan unchanged.
- Lock current endpoint paths and compact/detail/delta response schemas.

### Non-Functional

- Tests are deterministic and use fixed timestamps and fixtures.
- Characterization must not make tests depend on wall-clock timing or database/network access.
- Capture the existing 180/1,000/5,000 benchmark before v2 changes using the checked-in synthetic harness.

## Architecture And Data Flow

```text
create command
  -> idempotency lookup -> stored plan replay (no ranking)
  -> catalog snapshot + aggregate history
  -> v1 optimizer
  -> persisted winners, alternatives, scores
  -> unchanged compact response
```

This phase tests each boundary without introducing a new abstraction.

## Risk Assessment

| Risk | Mitigation |
|---|---|
| Brittle tests block safe refactoring | Assert business invariants and stable outputs, not private call order except replay no-work behavior. |
| Golden fixtures accidentally encode current bugs | Cross-check each golden against approved hard constraints and calorie derivation. |
| Local timing is mistaken for rollout evidence | Label runner metadata and retain staging p95 as a separate gate. |

## Security Considerations

- Use synthetic catalogs and history only.
- Never write raw user history, catalog ingredients, secrets, or database URLs to reports.
- Preserve owner-scoped/idempotent handler tests.
